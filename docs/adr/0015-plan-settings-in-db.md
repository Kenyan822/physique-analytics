# ADR-0015: 計画の設定は DB を正とする

- Status: Accepted
- Date: 2026-09-13

## Context

計画の設定（フェーズと目標ペース、栄養パラメータ、部位別 MEV/MRV、月次目標の起点）は `private/config.json` に置いていた。[ADR-0002](0002-separate-personal-data.md) に従って個人データを `private/` に隔離するためで、これ自体は正しい。

しかしこのファイルを読めるのは**手元で動く MCP だけ**だった。API サーバはファイルを持たない（Cloud Run のコンテナに `private/` は入らない）。

要件 N-05「当日の PFC 残量と目標を常に表示する」で、Web から目標値が必要になった。目標値は推定TDEE と目標ペースと栄養パラメータから決まるので、**API サーバが設定を読めないと計算できない**。

選択肢は3つあった。

1. API サーバにも `config.json` を配る（Secret Manager 経由で環境変数に載せる）
2. 設定を DB に移す
3. Web が MCP を呼ぶ

3 は MCP が stdio でしか動かない（[ADR-0010](0010-mcp-over-analysis-ui.md)）ので無理。

1 は動くが、**設定を変えるたびに Secret を更新してデプロイし直す**ことになる。要件 P-05「部位別 MEV/MRV、栄養パラメータを設定できる」がある以上、設定は画面から変えるもので、デプロイを伴うのはおかしい。

## Decision

**設定の正を DB に移す。** `config.json` は移行用の入力としてのみ残す。

- テーブル: `profile` / `plan_phases` / `nutrition_settings` / `volume_ranges` / `plan_blocks`
- API: `GET/PUT /v1/plan`、`GET/PUT /v1/plan/blocks`
- 移行: `cmd/planimport` で `config.json` を一度取り込む
- **MCP も DB を読む。** ファイルと DB の両方を正にしない

`private/` からデータが出ていくわけではない。DB は Supabase 上の自分専用のもので、[ADR-0002](0002-separate-personal-data.md) が禁じているのは「public なリポジトリに個人の実数値を書くこと」であり、DB に持つことではない。

## Consequences

### 良くなること

- 設定を画面から変えられる（要件 P-01 / P-05 / P-06）
- API が目標値を計算できる（要件 N-05）
- 設定の変更にデプロイが要らない

### 悪くなること・引き受けるリスク

- **設定が DB に入るので、DB を消すと計画も消える。** CSV エクスポート（要件 I-02）の対象は記録だけなので、設定は別途バックアップの対象になる
- `config.json` と DB が二重に存在する期間がある。取り込み後は `config.json` を「初期値の記録」として扱い、変更は DB 側で行う
- 月次目標（要件 P-02）は**保存しない**。起点とブロックから毎回計算する。要件 P-03（実測 LBM を起点に引き直す）がある以上、起点は変わる前提で、保存すると「引き直したつもりで古い表が残っている」が起きる

### やらなかったこと

**設定のバージョン管理をしない。** 「いつ計画を変えたか」を残す仕組みは入れていない。必要になったら `plan_phases` に有効期間を持たせるのではなく、変更履歴のテーブルを別に足す（期間を持たせると「今の計画」を引くクエリが複雑になる）。
