# ADR-0005: バーコードスキャン・Watch入力アプリ・消費カロリー取込を実装しない

- Status: Accepted
- Date: 2026-09-12

## Context

競合アプリが備えており、ユーザーからも期待されやすい3つの機能について、実装しない判断をした。**実装しない決定も記録に残す価値がある**ため ADR とする。

## Decision

以下を実装しない。

### 1. 食品のバーコードスキャン

商用食品データベースのライセンスが必要であり、個人プロジェクトでは調達できない。代替として3層構成をとる。

1. 日本食品標準成分表（公開データ）を基礎DBとしてインポート
2. 自作食品・自作レシピをユーザーが登録（材料から PFC を自動計算）
3. **よく使う食品を頻度順に表示し、食事セットでワンタップ記録**

**食品DBの網羅性で競合と競わない。** 実際に食べる食品は100品目程度に収束するため、頻出品目への最適化の方が入力は速くなる。

### 2. Apple Watch の入力アプリ

画面が小さく種目選択の操作が煩雑になるため、**iPhone より速くならない**。入力速度が非機能要件の最上位（1セット3秒以内）である以上、遅くなる選択肢は採らない。

**Watch はセンサーとして利用する。** HRV・安静時心拍・睡眠ステージを自動取得し、主観の疲労度（1-5）しかなかった回復モニタリングを客観指標で置き換える。

### 3. 消費カロリーの取り込み

スマートウォッチ・活動量計が算出する消費カロリーは誤差が±30%程度あり、TDEE 推定に使うと精度がむしろ下がる。**TDEE は摂取カロリーと体重トレンドから実測する**（[ADR-0003](0003-build-own-analytics.md)）ため、この値は不要。

同様に、手首の動きからのレップ自動カウントも精度が低く、RIR は結局手入力になるため実装しない。

## Alternatives considered

バーコードスキャンについては、無料の食品DB API の利用を検討した。しかし日本国内の商品カバレッジが低く、**中途半端な網羅性は「スキャンしたが見つからない」体験を生んで手入力より遅くなる**ため却下した。

## Consequences

**良い影響**

- 実装範囲が縮小し、Phase 1 を早く出せる
- **精度の低いデータをデータストアに持ち込まない。** 消費カロリーを記録すると、それを使った分析をしたくなり、誤った結論を導く
- 「作らない理由」が明文化され、後から機能追加を検討する際の判断材料になる

**悪い影響 / 受け入れるコスト**

- **初めて食べる食品は PFC を手で入力する必要がある**。特に運用開始直後の2週間は手間がかかる。以降は頻出品目が履歴に出揃うため軽くなる
- 同じ食品を表記ゆれで複数回入力すると履歴が分散する（正規化の仕組みを持たないため）
- ジムで iPhone を取り出す必要がある
- 競合アプリと機能比較した際、見劣りする項目が存在する

## Notes

この決定は**恒久的なものではない**。食品DBのライセンスが個人でも調達可能になった場合は再検討する。

### 2026-09-12 追記: Watch 入力アプリの却下理由に不備があった

上記「2. Apple Watch の入力アプリ」の却下理由は **「画面が小さく種目選択の操作が煩雑になる」** としていたが、これは**テンプレート機能（要件 T-06）を考慮していない**。

当日のメニューをテンプレートから呼ぶ運用では**種目は既に決まっており、Watch 上で選択する必要がない**。Watch に必要なのは重量・レップ・RIR の調整のみとなり、Digital Crown（物理ダイヤルのため汗をかいた手でも滑らない）で完結する。iPhone を取り出す動作が消える分、入力速度で上回る可能性がある。

**決定そのものは Phase 3 までは維持する**（Phase 1 のスコープを増やさないため）。ただし **Phase 4-B で実装する方針**に変更し、要件定義 §8 に記載した。HRR・インターバルタイマー・セット記録は同じ watchOS アプリで一括実装できるため、1つの単位として扱う。

なお「3. 消費カロリーの取り込み」および「レップ自動カウント」の却下理由は変わらない。**精度の低いデータをデータストアに持ち込まない**という判断は維持する。
