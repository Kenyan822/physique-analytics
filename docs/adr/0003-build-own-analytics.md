# ADR-0003: 分析ロジックを自作する

- Status: Accepted
- Date: 2026-09-12

## Context

トレーニング記録アプリ（Hevy 等）と食事記録アプリ（MacroFactor 等）は既に存在し、入力UXは数百人月をかけて磨かれている。これらを使わず自作する合理性を検討した。

当初は「入力は既存アプリ、分析だけ自作」という結論に達したが、後に Apple Health 連携を含めて再検討した。

## Decision

**分析レイヤーを自作する。記録レイヤーも段階的に自作するが、それは分析のためのデータ取得経路としてである。**

自作する分析ロジック:

| 分析 | 内容 |
|---|---|
| TDEE の動的推定 | 21日窓の線形回帰 × 7700kcal/kg。計算式ではなく実測から逆算する |
| e1RM | Epley + RIR補正。限界12レップ超は推定が崩れるため除外 |
| 部位別ボリューム | 13部位の MEV/MRV 判定（肩を前部/中部/後部、背中を広背筋/僧帽筋に分割） |
| 停滞検知 | 体重トレンド・摂取CV・e1RM傾き・HRV の複合条件 |

## Alternatives considered

**A. 既存アプリのみを使う**
却下。理由は2つ。

1. **データが分断される。** トレーニングと栄養が別アプリに分かれるため、「炭水化物量とトン数の相関」「睡眠と翌日のe1RM」のような統合分析ができない
2. **分析ロジックがブラックボックス。** 自分の仮説を検証できず、部位別セット数の MEV/MRV 判定や e1RM の回帰による停滞検知が存在しないか浅い

**B. 既存アプリ + CSVエクスポートして自作分析（当初の結論）**
部分的に採用。**Phase 1 完了までは実際にこの運用を行う。** ただし恒久的な解としては却下した。Apple Health を経由すれば体重・体脂肪率・歩数・睡眠を自動取得でき、入力の手間を既存アプリより減らせる余地があるため。この点を当初は過小評価していた。

## Consequences

**良い影響**

- トレーニング・栄養・体組成・回復指標が単一のデータストアに入り、統合分析が可能になる
- 分析ロジックが仕様として明文化され（[docs/03-分析ロジック.md](../03-分析ロジック.md)）、テスト可能な純粋関数として実装できる
- 自分の仮説を自分のデータで検証できる

**悪い影響 / 受け入れるコスト**

- **入力UXで既存アプリに劣るリスク。** これが実現すると3年の記録継続が破綻するため、入力速度を非機能要件として数値化した（1セット3秒以内・2タップ以内）
- **開発そのものが記録の代替行動になるリスク。** 対策を要件定義書 §6.4 に明記した
- 食品データベースを自前で持てない（[ADR-0005](0005-features-not-implemented.md)）

## Notes

### 2026-09-12 追記: 実装言語の方針は [ADR-0011](0011-go-analytics.md) で変更された

当初は Python 実装（`analysis/`）を**分析の正**とし、アプリ側はそれに合わせる方針だった。バックエンドを Go にし（[ADR-0006](0006-go-backend.md)）、MCP を分析の主経路にした（[ADR-0010](0010-mcp-over-analysis-ui.md)）結果、**分析ロジックの正は Go（`api/internal/analytics`）に移した**。

Python 実装は `reference/analysis/` に移動し、**Go 移植の検証基準**として保持する。「Go の出力が Python と一致すること」を受け入れ条件とする点は変わらない。

**分析を自作する**という本 ADR の決定自体は有効。変わったのは実装言語のみ。
