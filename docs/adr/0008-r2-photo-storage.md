# ADR-0008: 写真ストレージに Cloudflare R2 を採用する

- Status: Accepted
- Date: 2026-09-12

## Context

身体写真を月3枚（正面・側面・背面）保存する。当初は DB・認証と同じ Supabase Storage に置く想定だった（無料枠 1GB）。

しかし容量の試算が甘かった。**iPhone の写真は1枚3〜5MB あり、2MB 前提の試算では実態に合わない。**

| | 3年（108枚） | 6年（216枚） |
|---|---|---|
| 2MB 想定（当初の試算） | 216 MB | 432 MB |
| **実際（4MB）** | **432 MB** | **864 MB** |

Supabase Storage の 1GB では**6年でほぼ埋まる**。

加えて [02-データモデル.md](../02-データモデル.md) に記載の通り、**写真は3年計画において最終的に最も価値の高いデータになる**。体重が横ばいでも見た目が変わるフェーズが必ず来るため、そのとき数値だけでは進捗が見えない。容量のために解像度を落とすのは、この価値を毀損する。

## Decision

**写真は Cloudflare R2 に保存する。** DB・認証は Supabase のまま。

配信はアプリが発行する**短期の署名付きURL**で行い、公開URLは作らない。

## Alternatives considered

| | 無料枠 | egress | 東京 | 判定 |
|---|---|---|---|---|
| **Cloudflare R2** | **10 GB** | **無料・無制限** | ✓ | **採用** |
| Supabase Storage | 1 GB | 5 GB/月 | ✓ | 容量不足 |
| Cloud Storage (GCS) | 5 GB（US regions のみ） | 課金 | 無料枠では✗ | 東京が無料枠外 |
| AWS S3 | 12ヶ月のみ 5GB | 課金 | ✓ | 期限付き無料は個人の長期運用に不向き |

**Supabase Storage に統一する案を却下したのは容量。** 原寸で6年運用すると 864MB となり 1GB を圧迫する。リサイズで回避できるが、写真の価値を考えると解像度を落とす選択は取りたくない。

**R2 を選ぶ決め手は egress が無料である点。** Web で写真を時系列に並べて比較する機能（要件 B-07）を実装すると転送量が増えるが、R2 なら転送量を気にせず設計できる。Supabase の 5GB/月 でも当面足りるが、上限を意識しながら機能を作ることになる。

## Consequences

**良い影響**

- 容量が 1GB → 10GB になり、**原寸のまま6年以上運用できる**
- egress 無料のため、写真の閲覧頻度・一覧表示の実装を容量制約なしに設計できる
- S3 互換 API のため、将来別の S3 互換ストレージへ移行しやすい

**悪い影響 / 受け入れるコスト**

- **マネージドサービスが1つ増える**（Supabase + Cloud Run + Vercel + R2）。無料枠の管理対象が増える
- **Supabase Storage の RLS が使えない。** 行レベル認可の代わりに、API で**ユーザーの所有物か検証してから署名付きURLを発行する**必要がある。実装量は小さいが、認可ロジックを自分で持つことになる
- Cloudflare アカウントが必要になる

## Notes

保存対象は**身体写真のみ**とする。

| | 置き場所 |
|---|---|
| 身体写真（月3枚） | **R2** |
| トレーニング動画 | **保存しない**（[ADR-0005](0005-features-not-implemented.md) の方針。標準カメラアプリで足りる） |
| 週次レポート | DB（テキストのためストレージ不要） |
| CSV バックアップ | `private/` にローカル保存 + iCloud 同期 |

動画を保存対象に含めると容量が一桁変わる（1本50〜100MB）。要件でスコープ外としているため、この前提が崩れた場合は本 ADR を再検討する。
