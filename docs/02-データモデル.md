# データ設計 — 何を測るか、なぜそれか

分析可能なデータには3つの条件がある。「なんとなくメモする」が使えないのは、量ではなく**形式**の問題である。

1. 同じ列が毎回埋まる（自由記述ではなく固定スキーマ）
2. 測定条件が固定されている（時刻・服装・機器・タイミング）
3. 1つの問いに対応している

以下、各データを「これが無いと答えられない問い」とセットで定義する。答えるべき問いのないデータは取らない。記録が続かなくなる原因になる。

## 日付・時刻・単位の扱い

| | 決定 |
|---|---|
| **日付** | **JST（Asia/Tokyo）で決定する**（[ADR-0013](adr/0013-timezone-jst.md)）。端末のタイムゾーンに依存しない |
| 記録時刻 | `timestamptz`（UTC保存）。日付とは別に持つため、後から「何時に記録したか」の分析ができる |
| 週の区切り | **月曜始まり**（ISO 8601） |
| 質量 | **kg 固定**（lb には対応しない） |
| 長さ | **cm 固定** |
| エネルギー | **kcal 固定**（kJ には対応しない） |

海外滞在中も JST の日付で記録する。現地時間で記録すると帰国後のデータと時系列が繋がらなくなるため。

### 同期と削除

すべてのレコードが `updated_at` と `deleted_at` を持つ（[ADR-0014](adr/0014-sync-conflict-resolution.md)）。

- 競合は **`updated_at` が新しい方を採用**（Last Write Wins）
- **削除は物理削除しない。`deleted_at` を立てる**（物理削除するとオフライン側の古いレコードが復活しうる）
- クエリには常に `deleted_at IS NULL` を含める

## Tier 1 — 毎日 / 30秒（`data/daily.csv`）

ここが欠けると他のすべての分析が成立しない。

| 列名 | 測定条件 | これが答える問い |
|---|---|---|
| `weight_kg` | **起床直後・排尿後・裸・同じ体重計** | TDEE はいくつか / 減量ペースは適正か |
| `bodyfat_pct` | 同上（同時刻・同条件） | 参考値。単日では信用しない |
| `kcal` | その日の総摂取 | TDEE 推定の入力 |
| `protein_g` | 同上 | 減量中に LBM を守れているか |
| `fat_g` | 同上 | ホルモン維持の下限（体重×0.8g）を割っていないか |
| `carb_g` | 同上 | トレーニング強度が落ちる原因の切り分け |
| `sleep_h` | 睡眠時間 | 停滞・筋力低下の原因の切り分け |
| `steps` | 歩数 | **NEAT の変動（減量停滞の主犯はほぼこれ）** |
| `fatigue` | 起床時の主観 1-5 | オーバーリーチの早期検知 |
| `hrv_ms` | **Apple Watch 装着で自動** | 自律神経の疲労。体感より早く低下する |
| `resting_hr` | **同上** | 疲労・体調不良のサイン |
| `deep_sleep_min` | **同上** | 睡眠時間が足りていても質が低い場合を検出 |
| `note` | 自由 | 異常値の事後説明（外食・飲酒・病気） |

**下3列は Apple Watch を導入した場合のみ。** 現在の回復モニタリングは主観の `fatigue` と `sleep_h` だけで客観指標がなく、血液検査（年2回）の間を埋められない。Watch があれば HRV と安静時心拍で日次の客観判定ができる（判定閾値は [03-分析ロジック.md](03-分析ロジック.md)）。未導入なら空欄でよく、分析は自動でスキップされる。

**体重は毎日測る。** 日々のブレ（±1kg以上ある）は水分なので無視してよく、分析では7日移動平均しか使わない。毎日測る目的は**平均の精度を上げること**であって、その日の数字を見るためではない。

## Tier 2 — トレーニングごと（`data/workouts.csv`）

`date` / `exercise` / `set_no` / `weight_kg` / `reps` / **`rir`**

**`rir`（Reps In Reserve = あと何回できたか）が最重要列。** 「80kg×8回」だけでは限界だったのか余裕だったのか分からず、進捗が測れない。`80kg×8回 RIR2` なら推定1RMが計算でき、時系列で比較できる。

種目名の表記ゆれ（`ベンチ` / `ベンチプレス` / `BP`）は時系列を分断するので必ず統一する。部位への割り当ては種目マスタ（58種目・13部位）で管理する。

### 推定値と実測値を区別する

食事の PFC は、手入力と**写真からの AI 推定**（要件 N-06）の2経路で入る。**どちらで入ったかを記録に残す**（`source: manual | ai_estimated`）。

理由は TDEE 推定の精度に直結するため。推定値の比率が高い期間は、体重トレンドと摂取記録の整合が取れなくなる可能性がある。[03-分析ロジック.md](03-分析ロジック.md) の「記録漏れの疑い」判定と同様に、**推定値が多い週は判断の確度を下げて扱う**。

## Tier 3 — 週1回 / 日曜朝（`data/measures.csv`）

| 列名 | 測定位置 | これが答える問い |
|---|---|---|
| `neck_cm` | 喉仏の下 | 海軍式体脂肪率推定の入力 |
| `shoulder_cm` | 三角筋の最大周 | **「映える」の主指標。肩幅がV字を作る** |
| `chest_cm` | 乳頭の高さ | |
| `waist_navel_cm` | へそ | **体脂肪計より信頼できる脂肪の代理指標** |
| `hip_cm` | 臀部最大周 | |
| `arm_r_cm` | 上腕最大周（力こぶを作らず） | |
| `thigh_r_cm` | 股下10cm | 脚の伸びの追跡 |
| `calf_r_cm` | ふくらはぎ最大周 | |

**起床直後・食事前・同じメジャー・同じ強さ。** 朝一に固定するのは、日中の食事と姿勢でウエストが2〜3cm動くため。

**肩/ウエスト比が「映える」の定量指標**で、1.60 を超えると視覚的にV字が成立する。体脂肪率よりこちらを追う方が目的に忠実。

## Tier 4 — 写真 / 月1回（`data/photos/`）

`YYYY-MM-DD_{front,side,back}.jpg`。**同じ場所・同じ照明・同じ時刻（朝一・空腹）・同じポーズ・同じ距離。**

3年計画において写真は最終的に最も価値の高いデータになる。体重が横ばいでも見た目が変わるフェーズが必ず来るため、そのとき数値だけでは進捗が見えずモチベーションが折れる。目標像の写真がプロのライティングで2段階良く見えていたことからも、条件固定なしの比較は成立しない。

## Tier 5 — 年2回（`data/bloodwork.csv`）

減量期の後半（各年の仕上げ期の終盤）に必ず実施する。

総テストステロン / 遊離テストステロン / 甲状腺（TSH, FT3, FT4）/ 脂質（LDL, HDL, TG）/ 肝機能（AST, ALT, γ-GTP）/ フェリチン / ビタミンD / HbA1c

**目的は減量が内分泌を壊していないかの確認。** FT3 とテストステロンの低下は、減量が長すぎる/深すぎることの客観的シグナルであり、体感より早く出る。3年間（大会に出るなら毎年深く絞る）で健康を毀損しないための唯一の安全装置である。

## 記録しないと決めるもの

判断を鈍らせるノイズになるため、意図的に取らない。

- **スマートウォッチの消費カロリー** — 誤差±30%。TDEE は分析1で実測できるため不要
- **家庭用体組成計の部位別筋肉量** — 測定原理上、推定の推定
- **微量栄養素の全項目** — サプリで担保し、血液検査で年2回だけ検証
- **毎日の主観的な「見た目の調子」** — バイアスが大きく、写真で代替できる
