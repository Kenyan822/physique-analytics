# ADR-0017: 食品マスタを持つ。ただし「引数つきの計算式」として持つ

- Status: Accepted
- Date: 2026-09-21
- Supersedes: [docs/01-要件定義.md](../01-要件定義.md) N-02 の「**食品マスタは持たず、記録履歴がマスタになる**」

## Context

N-02 は当初こう決めていた。

> **過去の記録から頻度順に候補を出す**（食品マスタは持たず、記録履歴がマスタになる）

理由は妥当だった。食品マスタは**作るのも維持するのも重い**。自分が食べるものは100品目程度に収束するので、網羅的なマスタより頻出品目への最適化の方が実用的に速い。記録がそのままマスタになるなら、登録という作業自体が要らない。

**実際に使い始めて、前提が崩れた。**

**量が毎回違う。** プロテインを 30g の日と 45g の日がある。買った鶏むねが 230g の日と 310g の日がある。履歴は「そのとき記録した PFC の値」をそのまま写すので、**量が違えば使えない**。手で計算し直すことになり、それは記録しない理由になる。

**パッケージの表示が「n g あたり」で書かれている。** プロテインの袋には「30g あたり P24 F1.5 C2」と載っている。履歴ベースだと、これを「自分が飲む量ぶんに換算してから」記録することになる。**転記の途中で計算を挟むと間違える。**

**料理は材料ごとに量が変わる。** 鶏そぼろを作るとき、肉の量はその日買ったものに従う。砂糖と醤油は変えない。**1つの引数だけ動かしたい**のに、履歴には固定された結果しか無い。

## Decision

**食品マスタを持つ。引数は任意。**

### 基本 —— 引数なし

登録するのは**名前と PFC だけ**。選べばその値がそのまま入る。

```
プロテイン 1杯    P 24   F 1.5   C 2
```

**N-02 が避けたかった重さを持ち込まない。** 登録の手間は
「いま記録している内容 ＋ 名前」で、履歴から引くのとほぼ同じ速さで済む。

### 詳細 —— 引数を足す

量が変わるものだけ、**あとから引数を足せる**。

```
プロテイン
  量  g  基準 30   P 24   F 1.5   C 2   既定 30
```

入力時に `量 = 45` と入れると比例計算する。

```
P = 24 × (45 / 30) = 36
```

**引数は複数持てる。** これで料理も同じ形で書ける。

```
鶏そぼろ
  鶏ひき肉  g   基準 100   P 17.5  F 12.0  C 0     既定 200
  砂糖      g   基準 100   P 0     F 0     C 99.2  既定 10
  醤油      ml  基準 100   P 7.7   F 0     C 10.1  既定 15
```

買った肉が 230g なら、**鶏ひき肉だけ 230 に直せばよい**。

### 引数を任意にする理由

**大半の食品は量が固定。** 「ゆで卵1個」「コンビニのサラダチキン1個」は
毎回同じで、引数を作っても既定値のまま触らない。**触らない入力欄は邪魔**で、
爆速入力（#188）の逆を行く。

**登録の時点で「量が変わるか」は分からないことがある。** あとから足せる形に
しておけば、2回目に「これ量が毎回違うな」と気づいたときに直せる。
最初から全部に引数を持たせる設計だと、この判断を登録時に強いることになる。

### データの持ち方

**引数が無い項目には構成の行を作らない。**

| | |
|---|---|
| `food_items` | 名前 ＋ PFC（引数が無いときはこれを使う） |
| `food_item_components` | 引数。**あるときだけ行が入る** |

計算は「構成が空なら項目の PFC をそのまま返す」の1行で分岐する。

構成を必ず1行作る（基準量 1・既定 1）形も検討したが、**意味の無い行が
全項目に増える**うえ、画面側で「引数が無い」を判定するのに
`構成.count == 1 && 基準量 == 1` のような読みにくい条件が要る。

### 履歴ベース（N-02）は残す

**併存させる。** 一度しか食べないものは、いままでどおり履歴から引く。
**マスタへの登録を強制しない。**

覆すのは「マスタを持たない」であって、「履歴がマスタになる」ではない。

### 単位は表示専用

計算に要るのは `入力量 / 基準量` の比だけ。`g` / `ml` / `個` を型で縛らない。
卵1個なら基準量 1・単位「個」で同じ式に載る。

**単位を enum にしない理由**は `qty` と同じで、縛ると入力が止まるため。

## Consequences

### 良くなること

- **量が変わっても使える。** これが元の設計の最大の弱点だった
- **パッケージの表示をそのまま登録できる。** 換算を挟まないので転記で間違えない
- 料理の材料が1つ変わっても、**その引数だけ直せばよい**

### 悪くなること

- **登録という作業が増える。** N-02 が避けたかったもの。
  ただし**基本は名前と PFC だけ**で、いま記録している内容とほぼ同じ。
  引数を足すのは量が変わるものに限られる
- **テーブルが2つ増える**（項目と構成）。維持するスキーマが増える。
  ただし**構成は引数を足したときだけ行が入る**ので、多くの項目では空
- 既存の食事セット（N-03）と**役割が重なる**。あちらは「朝食セット」のように
  複数の食事をまとめて展開するもので、こちらは1つの食品の計算式。
  **統合しない** —— まとめる単位が違う（食事 vs 材料）

### 決めていないこと

- **記録との関係。** 展開した結果を `meals` に1行で入れるか、構成ごとに複数行か。
  1行にすると「何を食べたか」が名前だけになるが、複数行だと一覧が長くなる
- **位置情報での並べ替え**（N-08）。[要件定義 §4-C](../01-要件定義.md) の方針どおり
  **端末内だけ**で持つ。緯度経度をサーバに送らない

## 代替案

### A. 履歴のまま、量の換算だけ足す

「前回 30g で記録した。今回は 45g」と入れたら比例させる。

**採らない。** 履歴の1件に基準量の情報が無い。「30g で P24」の記録から
「この 30 は基準量だ」とは読めない ——「1個」で記録したものもあるし、
量を書かずに記録したものもある。**基準量は登録時に宣言されるべき情報。**

### B. 外部の食品データベースを引く

**採らない。** 日本の市販品の網羅性が低く、結局手で入れることになる。
[要件定義](../01-要件定義.md) の「網羅性より頻出品目への最適化」という判断は
いまも有効で、**変わったのは「量が固定か可変か」だけ**。
