# アプリ要件定義書

- 作成日: 2026-09-09
- 対象: トレーニング・食事・体組成の記録と分析を統合するアプリ
- プラットフォーム: **iOS (Swift/SwiftUI) + Web (Next.js)**

## 1. 背景と目的

### なぜ自作するのか

既存アプリ（Hevy / MacroFactor 等）の入力UXは優れているが、**構造的に解決できない問題が2つある**。


| 問題         | 内容                                                                                    |
| ---------- | ------------------------------------------------------------------------------------- |
| **データの分断** | トレーニングと栄養が別アプリに分かれ、統合分析ができない。「炭水化物量とトン数の相関」「睡眠と翌日のe1RM」を誰も見られない                       |
| **分析の浅さ**  | 部位別週間セット数の MEV/MRV 判定、e1RM の回帰による停滞検知、TDEE と挙上重量の同時追跡がない。分析ロジックがブラックボックスで自分の仮説を検証できない |


自作の勝ち筋はここにある。加えて **Apple Health を経由すれば体重・歩数・睡眠が自動で入る**ため、入力の摩擦は既存アプリより低くできる余地がある。

### 目的

**3年計画を3年間完走させること**。そのために必要な機能だけを作る。「あったら便利」は作らない。

### 最大のリスクを最初に書いておく

**このアプリの失敗要因は機能不足ではなく、開発が記録の代替行動になることである。** 肉体改造のためのアプリ開発は達成感を伴う作業であり、トレーニングと栄養管理の代替になりやすい。対策を非機能要件に含める（§6.4）。

## 2. スコープ

### やること

- トレーニング記録（種目・重量・レップ・RIR）
- 食事記録（PFC・kcal）
- 体組成・周囲長・写真の記録
- Apple Health 連携（体重・歩数・睡眠の自動取得）
- 分析（TDEE動的推定・e1RM・部位別ボリューム・停滞検知）
- 計画管理（フェーズ・月次目標・大会カウントダウン）
- CSV エクスポート

### やらないこと


| やらないこと             | 理由                                                                   |
| ------------------ | -------------------------------------------------------------------- |
| バーコードスキャン          | 商用食品DBのライセンスが必要。ユーザー辞書方式で代替（§5.2）                                    |
| SNS・フォロー機能         | 1人用。作る価値がない                                                          |
| 動画・フォームチェック        | スコープ外。標準のカメラアプリで足りる                                                  |
| ワークアウトプラン自動生成      | 配分は別途決定済み。手で組む                      |
| Apple Watch の入力アプリ（**Phase 3 まで**） | Phase 1〜3 では実装しない。Watch はセンサーとして使い、入力は iPhone。**Phase 4-B で実装する方針**（§8） |
| マルチユーザー・課金         | 本人1人。ただしデータモデルは user_id を持つ（§7）                                      |


## 3. ユーザーと利用シーン

利用者は本人1人。プラットフォームごとに役割を明確に分ける。


| シーン        | 場所・状況                | プラットフォーム      | 求められること              |
| ---------- | -------------------- | ------------- | -------------------- |
| **セット記録**  | ジム。汗をかいた手、片手操作、電波が悪い | **iOS**       | **1セット3秒以内・オフライン必須** |
| 食事記録       | 食事の直後、移動中            | iOS           | よく使う食品を3タップ以内        |
| 朝の計測       | 起床直後                 | iOS（Health自動） | 体重・体脂肪率は体重計から自動      |
| 週1の計測      | 日曜朝                  | iOS           | 周囲長8箇所 + 写真3枚        |
| **週次レビュー** | 自宅、落ち着いて             | **Web**       | 大きい画面でグラフと判断材料を見る    |
| 計画の見直し     | 各フェーズ完了時             | Web           | 月次目標の引き直し            |


**iOS = 入力、Web = 分析。** この分担を崩さない。Webに入力機能を作り込むと、両方が中途半端になる。

## 4. 機能要件

### 4.1 トレーニング記録（iOS 主体）


| ID   | 要件                                          | 優先度 |
| ---- | ------------------------------------------- | --- |
| T-01 | 種目を選び、重量・レップ・RIR を記録できる                     | 必須  |
| T-02 | **前回同種目の重量・レップ・RIR をデフォルト表示する**（前回踏襲が最頻ケース） | 必須  |
| T-03 | 重量・レップは +/- ボタンで刻み調整（重量2.5kg刻み、レップ1刻み）      | 必須  |
| T-04 | セット完了後、次セットの入力欄が自動で開く                       | 必須  |
| T-05 | インターバルタイマー（種目ごとに既定値、通知あり）                   | 必須  |
| T-06 | 当日のメニューをテンプレートから呼び出せる（Day1〜Day6）            | 必須  |
| T-07 | オフラインで完全に動作し、オンライン復帰時に同期する                  | 必須  |
| T-08 | 種目マスタ（58種目・13部位）を管理でき、部位が自動で紐づく             | 必須  |
| T-09 | 記録中に前回のトン数・e1RM を表示する（その場で超えられるか判断）         | 推奨  |
| T-10 | セットの並び替え・削除・種目の差し替え                         | 推奨  |


**T-02 が最重要。** ジムでの入力の大半は「前回と同じか、少し増やす」であり、デフォルト値が正しければ操作は1〜2タップで済む。

### 4.2 食事記録（iOS 主体）


| ID   | 要件                                  | 優先度 |
| ---- | ----------------------------------- | --- |
| N-01 | 食品名・量・PFC・kcal を入力して記録できる | 必須  |
| N-02 | **過去の記録から頻度順に候補を出す**。あわせて**引数つきの食品マスタ**を持つ（[ADR-0017](adr/0017-food-master-with-parameters.md) で方針を変更） | 必須  |
| N-03 | 「食事セット」を登録できる（朝食セット等をワンタップで記録）      | 必須  |
| N-04 | 前日・過去の食事をコピーできる                     | 必須  |
| N-05 | 当日の PFC 残量と目標を常に表示する（§4.4 の目標値と連動）  | 必須  |
| N-06 | **食事の写真（+任意のテキスト）から PFC を推定する** | 必須 |
| N-07 | 目標に対する不足分を満たす食品を提案する | 任意 |
| N-08 | **位置情報に基づき、その場所で過去に食べたものをサジェストする** | 任意（Phase 4） |


**食品マスタという概念を持たない。** 「食品を登録する」という作業を設けず、記録時に名前と PFC を直接入力する。**過去の記録がそのまま候補になる**ため、2回目以降は履歴から選ぶだけで済む。

この設計にした理由は3つ。

1. **公的な食品成分表はインポートしない。** 収載名が「こめ［水稲めし］精白米 うるち米」形式で検索しづらく、市販品（コンビニ弁当・プロテイン・サプリ）が収載されていない。実装コスト（Excelのパース・名称正規化・検索インデックス）に見合わない
2. **自作食品の登録機能も持たない。** マスタ登録という別作業を挟むと、記録の摩擦が増える。記録した時点でマスタが育つ方が速い
3. **レシピの材料からの自動計算も不要。** 自炊でも完成品の PFC を1回入力すれば、次からは履歴で呼べる

**N-02・N-03 が入力速度を決める。** 自分が食べる食品は100品目程度に収束するため、網羅性より頻出品目への最適化が実用的に速い。

#### N-06: 写真からの PFC 推定

**食品マスタを持たない設計の弱点は「初めて食べるものの入力」**であり、ここを Vision 対応の LLM で埋める。

```
写真を撮る ──┐
             ├──▶ LLM ──▶ PFC推定値 ──▶ 【編集可能な形で提示】──▶ 確認して記録
テキスト補足 ─┘
（任意・精度が上がる）
```

- テキスト補足は任意だが、**「鶏むね200g、白米150g」のように量を添えると精度が大きく上がる**（写真だけでは食器のサイズが分からず量の推定が難しい）
- **推定結果をそのまま保存しない。** 必ず編集可能な形で提示し、ユーザーが確認してから記録する
- **推定値であることをデータに残す**（`source: manual | ai_estimated`）。TDEE 推定の精度に直結するため、後から精度を評価できるようにする

**コスト試算**: 1日3食 × 365日 = 年1,095回。1回あたり入力約1,700トークン・出力約200トークンとして、Claude Haiku 4.5 相当なら**年間3ドル程度**。無料枠ではないが、実用上は無視できる。

| ID | 要件 | 優先度 |
|---|---|---|
| I-01 | **CSV インポート**（`daily.csv` / `workouts.csv` / `measures.csv` を既存スキーマで取り込む） | **必須（Phase 1a）** |

**I-01 が Phase 1a に必須な理由。** 記録は 2026-09（P0）から始まるが、アプリの完成は Phase 1 完了後になる。**その間の数ヶ月分を CSV で記録する**運用のため、取り込み手段がないとデータが分断される。

対応するのは**このプロジェクトの CSV スキーマのみ**。Hevy 等の外部アプリの形式には直接対応せず、必要なら手元のスクリプトで変換する（外部サービスの形式に依存すると壊れやすいため）。

### 4.7 Apple Watch（センサーとして利用）

**Watch は入力デバイスではなくセンサーとして使う。** セット記録の入力は iPhone より速くならないため作らない。価値は取得できるデータの側にある。

現在の回復モニタリングは**主観の疲労度1-5と睡眠時間だけ**で、客観指標がない。血液検査は年2回しかないため、その間を埋める日次の指標が不足している。


| データ                | 分かること                  | どこに効くか                        |
| ------------------ | ---------------------- | ----------------------------- |
| **HRV（心拍変動・SDNN）** | 自律神経の状態。**体感より早く低下する** | オーバートレーニングの早期検知。減量ペースを緩める判断材料 |
| **安静時心拍（RHR）**     | 毎朝自動記録。上昇は疲労・体調不良のサイン  | 同上。HRVと組み合わせて精度を上げる           |
| **睡眠ステージ**         | 深睡眠・REM の内訳（現在は時間のみ）   | 「睡眠6.5h未満」より正確な回復判定           |
| 歩数（常時装着）           | iPhone より高精度           | NEAT の追跡精度（減量停滞の主犯）           |


#### 判定の閾値


| 指標         | 警告ライン                      | 対応                    |
| ---------- | -------------------------- | --------------------- |
| HRV 7日平均   | baseline（30日平均）から **-15%** | 回復週を前倒し / 減量ペースを1段落とす |
| 安静時心拍 7日平均 | baseline **+5 bpm**        | 同上                    |
| 深睡眠 7日平均   | 60分未満                      | 睡眠を減量ペースより優先する        |


**これらは既存の「疲労7日平均 &gt; 3.5」「睡眠 &lt; 6.5h」というアラートを、主観から客観へ置き換えるもの。**

#### 実装しないもの


|               | 理由                                                                             |
| ------------- | ------------------------------------------------------------------------------ |
| 消費カロリーの取り込み   | 誤差±30%。[02-データモデル.md](02-データモデル.md) で「記録しない」と決めた項目で、Watch でも精度は改善しない。TDEE は実測で出す |
| レップ自動カウント     | 手首の動きからの推定は精度が低く、RIR は結局手入力になる                                                 |
| トレーニング中の心拍ゾーン | 筋トレでは有酸素ほど意味を持たない。使うならセット間の心拍回復（HRR）                                           |


#### watchOS アプリが必要な範囲・不要な範囲

**HRV・安静時心拍・睡眠ステージは、watchOS アプリを作らずに取得できる。** Apple の標準機能が計測して HealthKit に書き込み、iPhone に自動同期されるため、iPhone アプリが HealthKit から読むだけで済む。

```
Apple Watch                   iPhone
┌──────────┐                ┌──────────┐
│ 心拍・HRV │  自動同期       │ HealthKit│
│ 睡眠計測  │───────────────▶│          │──▶ アプリ
└──────────┘                └──────────┘
  Apple標準が書き込む             読むだけ
```

| やりたいこと | watchOSアプリ | 接続方法 |
|---|---|---|
| **HRV・安静時心拍・睡眠ステージ** | **不要** | HealthKit のみ |
| 歩数・体重（体重計から） | 不要 | HealthKit のみ |
| セット間の心拍回復（HRR） | **必要** | WatchConnectivity |
| Watch でのインターバルタイマー（触覚） | **必要** | WatchConnectivity |
| Watch でのセット記録 | **必要** | WatchConnectivity |

**この境界が見積もりを左右する。** 回復モニタリング（B-09 / A-14）は iPhone の HealthKit 連携に読み取り型を3つ足すだけで実現でき、追加コストはほぼゼロ。一方、Watch 側で何かを「する」機能は、別ターゲット・別UI・WatchConnectivity の同期処理・バッテリー考慮が一式必要になり、コストが一段跳ね上がる。

#### 実装のキモ: バックグラウンド更新

`HKObserverQuery` + `enableBackgroundDelivery` を使い、**新しいデータが入った時点でアプリを起こして同期する**。これがないと「アプリを開いたときだけ同期」になる。

```swift
let query = HKObserverQuery(sampleType: hrvType, predicate: nil) { _, completion, _ in
    // 新しい HRV が入った → サーバに同期
    completion()
}
healthStore.execute(query)
try await healthStore.enableBackgroundDelivery(for: hrvType, frequency: .daily)
```

**ユーザーが何もしなくてもデータが溜まる状態**を作れるかが、3年継続できるかの分かれ目になる。

#### 前提

- **SE で十分。** HRV・RHR・睡眠ステージ・歩数はすべて取得できる。上位モデルとの差（血中酸素・心電図・常時点灯）はこの用途では効かない
- **毎晩の充電運用が必要。** 起床時 HRV は睡眠中の計測から出るため、就寝時に装着していなければ取れない。入浴時に充電する習慣を作れるかが実運用の分かれ目

### 4.8 入力値の検証

記録は3年間蓄積され、**異常値が混ざると分析全体が歪む**（特に体重トレンドの線形回帰）。

| 対象 | 検証 |
|---|---|
| 体重 | 30〜200kg の範囲内。かつ**前回記録から ±5kg 以上動いたら確認を求める**（桁の打ち間違い検出） |
| 体脂肪率 | 3〜50% |
| 日付 | **未来日を許可しない** |
| 重量・レップ・RIR | 負値を許可しない。RIR は 0〜10 |
| 摂取 kcal | 500〜6000 |
| 周囲長 | 前回から ±10cm 以上動いたら確認を求める |

**エラーで弾くのではなく確認を求める**方針。桁の打ち間違い（7.68kg / 768kg）は弾くべきだが、減量期に本当に 2kg 落ちることはある。**判断はユーザーに委ね、機械は「異常かもしれない」と伝えるだけにする。**

### 4.9 種目マスタの初期投入

種目マスタ（58種目・13部位）は**マイグレーションのシードとして投入する**。アプリ起動後に手動登録させない。

部位の割り当ては [02-データモデル.md](02-データモデル.md) の方針に従う。新種目の追加はアプリから行えるようにする（T-08）。

## 5. 技術的に難しい点と方針

### 5.1 オフライン同期

ジムは電波が悪く、記録中の通信は前提にできない。

- **iOS はローカルDBを正とし、バックグラウンドで同期する**（SwiftData / Core Data）
- 競合はほぼ起きない（1ユーザー・単一デバイス入力）が、**更新時刻の新しい方を採用**する単純な解決で足りる
- 同期状態をUIに出す（未同期セット数のバッジ）

### 5.2 食品データベース

**バーコードスキャンは商用DBのライセンスが必要なため実装しない。** 代替方針は3層。

1. **日本食品標準成分表**（文部科学省・公開データ）をインポートして基礎DBにする
2. **自作食品・自作レシピ**をユーザーが登録（材料から PFC を自動計算）
3. **よく使う食品**を頻度順に並べ、食事セットでワンタップ記録

自分が食べる食品は100品目程度に収束するため、**網羅性より頻出品目への最適化が実用的に速い**。

### 5.3 既存資産との関係

**CSV エクスポートは維持する。** アプリの DB から `daily.csv` / `workouts.csv` / `measures.csv` を同じスキーマで書き出せる状態を保つ。

理由は2つ。

1. **Go 実装の検証基準。** Phase 0 の Python プロトタイプ（`reference/analysis/`）が動く状態を保つことで、Go 実装の出力と比較できる（[ADR-0011](adr/0011-go-analytics.md)）
2. **バックアップの正。** Supabase の無料枠は7日保持のため、長期保管は CSV で行う（[ADR-0002](adr/0002-separate-personal-data.md)）

## 6. 非機能要件

### 6.1 入力速度（最重要）

**これを満たせなければアプリを作った意味がない。** 既存アプリに劣る入力速度では3年もたない。


| 操作             | 目標                      |
| -------------- | ----------------------- |
| 1セットの記録（前回踏襲）  | **3秒以内・2タップ以内**         |
| 1食の記録（食事セット使用） | **5秒以内・3タップ以内**         |
| 朝の体重・体脂肪率      | **0秒**（Apple Health 自動） |
| アプリ起動から記録開始まで  | 2秒以内                    |


### 6.2 可用性・データ保全

- オフラインで記録機能が完全に動作する
- **データ喪失は許容しない。** ローカル保存 + サーバ同期 + CSV エクスポートの三重化
- 写真はサーバに保存（端末紛失で3年分を失わないため）

### 6.3 プライバシー

- 体組成・写真・血液検査は**センシティブな個人データ**として扱う
- 認証必須。写真は署名付きURLで非公開配信
- 外部サービスへのデータ送信は行わない

### 6.4 開発が代替行動にならないための制約

**§1 で挙げた最大のリスクへの対策を要件に含める。**


| 制約               | 内容                                                |
| ---------------- | ------------------------------------------------- |
| **記録の停止は許されない**  | アプリ完成を待たず、2026-09 から既存の CSV で記録を開始する。アプリはできたら移行する |
| **開発時間の上限**      | 週あたりの開発時間を決め、トレーニング・睡眠・食事管理を圧迫しない                 |
| **Phase 1 を最小に** | 動くものを早く出す。作り込みは後（§8）                              |
| **完成の定義を先に決める**  | Phase 1 の受け入れ条件（§8）を満たしたら、次の機能に進む前に4週間使う          |


## 7. データモデル（概略）

**すべてのテーブルが `created_at` / `updated_at` / `deleted_at` を持つ**（[ADR-0014](adr/0014-sync-conflict-resolution.md)）。以下では省略している。

                 fat_g, carb_g, sleep_h, steps, fatigue, note,
                 hrv_ms, resting_hr, deep_sleep_min   -- Watch 装着時のみ
                 └ UNIQUE(user_id, date)

meal_entries     user_id, date, meal_type, name, amount, kcal, p, f, c,
                 source(manual|ai_estimated), photo_key
                 -- 食品マスタを持たないため、記録が名前とPFCを直接持つ
meal_sets        id, user_id, name  /  meal_set_items(meal_set_id, name, amount, kcal, p, f, c)

`user_id` は1人でも持つ。後から複数ユーザーに広げる余地を残すコストは低い。

## 8. 段階的リリース

**Phase 1 を小さく切り、4週間使ってから次に進む。**

**開発順序は Web 先行**（[ADR-0009](adr/0009-web-first-with-input.md)）。1人開発では反復の速さが完了時期を直接左右するため、基盤（スキーマ・API・認証・デプロイ）を最も検証しやすい環境で先に固める。

### Phase 1 — 記録が回る状態（目標: 6〜8週）

**API + DB + Web で「記録して週次レポートを見る」ループを完成させる。**

スコープが広いため内部を2つに割る。

#### Phase 1a — 基盤とトレーニング記録（4〜5週）

- `openapi.yaml` の設計（Phase 全体の起点。ここが決まらないと Go も Web も書けない）
- Go API: 認証、トレーニング記録の CRUD
- DB: スキーマ + マイグレーション
- Web: トレーニング記録の入力（T-01〜T-06, T-08）、テンプレート管理
- デプロイ: Cloud Run + Supabase + Vercel

**受け入れ条件**
1. ブラウザから当日のテンプレートを呼び、セットを記録できる
2. 前回同種目の重量・レップ・RIR がデフォルト表示される（T-02）
3. CSV エクスポートした結果で `reference/analysis/analyze.py` が動く（スキーマ互換の確認）
4. **2週間、実際のトレーニングで使って記録が途切れない**

#### Phase 1b — 日次記録と MCP サーバー（2〜3週）

- Web: 日次記録の入力（体重・体脂肪率・PFC・睡眠・歩数・疲労）
- Web: **今週のサマリのみ常設表示**（体重トレンド・PFC残量・今週のアクション）
- **MCP サーバー**（§Phase 4-A に定義したツール群）— 分析と計画管理はここから行う

**受け入れ条件**
1. 毎日の記録が1画面で完結する
2. **MCP 経由で取得した週次レポートが `reference/analysis/analyze.py` の出力と一致する**
3. Claude Code から「先月と今月の部位別ボリュームを比較して」のような質問に答えられる
4. 大会カウントダウンと必要ペース判定が動く（A-10）

> **分析UIは作らない**（[ADR-0010](adr/0010-mcp-over-analysis-ui.md)）。グラフ・期間比較・計画の引き直しは MCP 経由で Claude Code に依頼する。

> **Phase 1 の期間は体重・歩数・睡眠を手入力する。** HealthKit 連携は Phase 2 まで入らない。

### Phase 2 — iOS（目標: 5〜6週）

**iOS の存在理由は「ジムでの入力速度」と「HealthKit 連携」の2点に集約される。** それ以外は Web で足りる。

- iOS: トレーニング記録（T-01〜T-10）。**1セット3秒以内・2タップ以内**に最適化
- iOS: オフライン動作と同期（T-07）
- iOS: **HealthKit 連携**（B-01, B-09）— 体重・体脂肪率・歩数・睡眠・HRV・安静時心拍
- Phase 1 で確定した `openapi.yaml` から Swift クライアントを生成する

**受け入れ条件**
1. 1セットの記録が3秒以内・2タップ以内で完了する
2. 機内モードで完全に動作し、復帰時に同期される
3. **体重・歩数・睡眠の手入力がゼロになる**（HealthKit から自動取得）
4. 2週間、ジムで実際に使って iPhone を取り出す以外の摩擦がない

### Phase 3 — 食事・計測・計画（目標: 5〜6週）

- 食事記録（N-01〜N-06）: Web と iOS の両方
- **写真からの PFC 推定（N-06）**: 初めて食べるものの入力コストを下げる
- 周囲長（B-02, B-03）・写真（B-04, B-05, B-07）
- 計画管理の完成（P-02, P-03, P-06）— 月次目標の引き直し

**受け入れ条件**
1. 1食の記録が5秒以内・3タップ以内（食事セット使用時）
2. 写真1枚から PFC 推定値が提示され、編集して記録できる
3. 写真撮影時に前回写真がガイド表示される（B-05）
4. 実測 LBM を起点に月次目標を再生成できる（P-03）

### Phase 4 — 以降（優先度順に随時）

#### 4-A. MCP サーバーの拡張

> **MCP サーバー本体は Phase 1b で実装する**（[ADR-0010](adr/0010-mcp-over-analysis-ui.md)）。ここでは Phase 1 以降に追加するツールを扱う。

**目的: 3年分のデータに対して、事前に定義していない質問ができるようにする。**

週次レポート（§4.4）は固定フォーマットであり、決めた項目しか見られない。MCP サーバーとして公開すれば、Claude Code から自然言語で問い合わせられる。

想定する質問の例:

- 「2027年3月と2028年3月で、同じ体脂肪率のときの肩囲を比較して」
- 「睡眠6時間未満だった翌日、ベンチの e1RM は平均でどれくらい落ちてる？」
- 「先月のミニカット中、どの部位のボリュームが落ちた？」
- 「大会前の減量で、過去2回のうちどちらの方が LBM を守れた？」

**これらは事前に実装できない。** 質問が生まれるのは、データが溜まって仮説が立ってからである。固定レポートでは構造的に対応できない領域。

| ツール | 用途 |
|---|---|
| `get_daily_logs(from, to)` | 日次記録（体重・PFC・睡眠・歩数・HRV） |
| `get_workouts(from, to, exercise?, muscle?)` | トレーニング記録。種目・部位でフィルタ |
| `get_measurements(from, to)` | 周囲長 |
| `get_volume_summary(week)` | 部位別の有効セット数・トン数 |
| `estimate_tdee(asof)` | 任意時点の TDEE 推定 |
| `get_e1rm_trend(exercise, weeks)` | 種目別の推定1RM と回帰の傾き |
| `generate_weekly_report(asof)` | 週次レポートの生成（既存ロジック） |

**実装方針**

- **Go で実装し、API と同じ分析パッケージ（`api/internal/analytics`）を共有する**（[ADR-0011](adr/0011-go-analytics.md)）。同一バイナリ・同一デプロイに乗るため運用対象が増えない
- **読み取り専用。** 記録の作成・更新はアプリから行い、MCP は参照のみ
- **ローカル実行（stdio transport）のみ。** 体組成・写真・血液検査を扱うため、リモート MCP サーバーにはしない

**API と分析パッケージを共有するため、ツール定義を足すだけで済む。** これが Phase 1 に前倒しできる理由であり、分析UIを作り込まない判断の根拠でもある（[ADR-0010](adr/0010-mcp-over-analysis-ui.md)）。

#### 4-B. Apple Watch の拡張

§4.7 で定義した HRV・安静時心拍・睡眠ステージに加えて、以下を検討する。

| | 内容 | 評価 |
|---|---|---|
| **Watch でのセット記録** | 当日のテンプレートに沿った重量・レップ・RIR の入力 | **実施する方針**。当初 [ADR-0005](adr/0005-features-not-implemented.md) で却下したが、却下理由がテンプレート機能（T-06）を考慮していなかった。下記参照 |
| **インターバルタイマー（触覚）** | セット完了で自動開始、触覚で通知 | Watch 入力とセットで実装する。ポケットの iPhone より確実に気づく |
| **セット間の心拍回復（HRR）** | セット終了後60秒での心拍低下幅 | 体力・回復力の客観指標。Watch でセッションを持つなら同時に取れる |
| ワークアウトの自動検出 | Watch のワークアウト機能と記録を紐付け | 記録忘れの検出に使える |
| トレーニング中の平均心拍 | セッション全体の負荷指標 | 筋トレでは有酸素ほど意味を持たない。優先度低 |

**Watch 入力の設計方針**

却下時の前提は「種目選択が画面上で煩雑になる」だったが、**テンプレート（T-06）から当日のメニューを呼ぶ運用では種目は既に決まっている**。Watch に必要なのは重量・レップ・RIR の調整だけになる。

| | |
|---|---|
| Watch で行う | **当日テンプレートに沿ったセット記録のみ**。重量は Digital Crown、レップ/RIR は +/- ボタン |
| iPhone で行う | 種目の追加・差し替え、テンプレート編集、食事記録、周囲長・写真 |

**Digital Crown は物理ダイヤルであり、汗をかいた手でも滑らない。** iPhone を取り出す動作自体が消える点も含め、入力速度（1セット3秒以内）を上回れる可能性がある。

ただし **HRR・タイマー・セット記録は同じ watchOS アプリで一括実装できる**ため、Phase 4-B はこれらをまとめて1つの単位として扱う。

**HRR を採るなら、セットの終了時刻を記録する必要がある**（現在はセット単位の時刻を持っていない）。データモデルの変更を伴うため、Phase 4 で必要性を再評価する。

#### 4-C. 位置情報ベースのサジェスト（N-08）

**特定の場所に入ったとき、そこで過去に食べたもの・やったことをサジェストする。**

| 場所 | サジェスト内容 |
|---|---|
| よく行く定食屋・カフェ | 過去にその店で記録した食事 |
| ジム | 当日のトレーニングテンプレートを開く |

外食は**食品マスタを持たない設計の弱点が最も出る場面**（メニューの PFC が分からない）。一度記録すれば次から履歴で呼べるが、**「どの店にいるか」を手がかりにできれば候補を数件に絞れる**。

実装は Core Location のジオフェンス（特定の座標+半径への進入検知）。

**プライバシー方針: 位置情報は端末内で処理し、サーバには送らない。** サーバが持つのは「場所の名前」と、その場所に紐づく食事記録のみ。緯度経度は端末のローカルDBに置く。
