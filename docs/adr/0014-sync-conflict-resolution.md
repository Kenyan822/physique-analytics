# ADR-0014: 同期の競合は Last Write Wins + 論理削除で解決する

- Status: Accepted
- Date: 2026-09-12

## Context

当初のアーキテクチャでは「iOS = 入力、Web = 分析」と役割を分けていたため、**入力経路が1つ**だった。[04-アーキテクチャ.md](../04-アーキテクチャ.md) には「競合はほぼ起きない（1ユーザー・単一デバイス入力）」と記載していた。

しかし [ADR-0009](0009-web-first-with-input.md) で **Web にも入力機能を持たせた**結果、この前提が崩れた。

```
1. ジムで iOS に記録（オフライン。ローカルDBに保存）
2. 帰宅後、Web で同じ日の記録を修正
3. iOS がオンラインに復帰して同期 ← ここで競合
```

さらに悪いケースとして、**Web で削除したレコードを、iOS が「更新」として送り返して復活させる**ことが起こりうる。

## Decision

**Last Write Wins（更新時刻の新しい方を採用）を基本とし、削除は論理削除で表現する。**

### ルール

| | 内容 |
|---|---|
| 比較キー | `updated_at`（`timestamptz`） |
| 解決 | **`updated_at` が新しい側を採用する** |
| 削除 | **物理削除しない。`deleted_at` を立てる**（tombstone） |
| 削除の扱い | 削除も「`deleted_at` を設定する更新」として LWW の対象にする |
| 競合検知 | サーバ側の `updated_at` がクライアントの保持する値より新しい場合、**同期時にユーザーへ通知する**（自動マージはしない） |

### なぜ論理削除が必要か

物理削除にすると、**削除されたレコードが「存在しない」ため LWW の比較対象にならない**。オフライン側が持つ古いレコードを送り返すと、削除が無かったことになって復活する。

`deleted_at` を持てば削除も1つの更新になり、時刻比較で正しく解決できる。

```
Web:  14:00 に削除 → deleted_at = 14:00, updated_at = 14:00
iOS:  13:50 に更新 → updated_at = 13:50
同期: 14:00 > 13:50 なので削除が勝つ ✓
```

## Alternatives considered

**A. CRDT / OT による自動マージ**
却下。**1ユーザーの個人アプリに対して過剰**。実装コストが大きく、デバッグも難しい。競合の発生頻度（月に数回あるかどうか）に見合わない。

**B. サーバ側を常に正とする（クライアントの変更を破棄）**
却下。**オフライン優先の設計と矛盾する**。ジムでオフライン記録した内容が、同期時に消える可能性がある。記録が消えることは3年計画で最も避けるべき事象。

**C. 競合時に必ずユーザーへ選択させる**
却下。競合の大半は「同じ内容の更新」であり、毎回選択を求めると摩擦が大きい。**LWW で自動解決し、通知だけ出す**方が実用的。

**D. レコード単位ではなくフィールド単位でマージ**
却下。「体重は iOS が新しく、睡眠時間は Web が新しい」を正しくマージできるが、実装が複雑になる。**1ユーザーが同じレコードを同時編集する頻度は低い**ため、レコード単位で足りる。

## Consequences

**良い影響**

- **オフライン記録が消えない。** ジムでの記録が同期時に失われることがない
- 削除が正しく伝播し、復活しない
- 実装が単純（`updated_at` の比較のみ）

**悪い影響 / 受け入れるコスト**

- **同時編集した場合、片方の変更が失われる。** LWW の本質的な性質であり、これは受け入れる。競合を検知して通知することで、ユーザーが気づける状態にする
- **論理削除のためテーブルが肥大化する。** ただし3年で数万行程度なので実害はない。必要なら1年以上前の tombstone を定期削除する
- **すべてのクエリで `deleted_at IS NULL` を条件に加える必要がある。** 漏れるとゴーストデータが表示される。sqlc のクエリ定義で統一する

## Notes

**実際に競合が起きる場面は限定的。** ジムでは iOS、自宅では Web という使い分けになるため、同じレコードを同時に触ることは稀である。この ADR は「稀に起きたときにデータが壊れない」ための保険であり、日常的に機能するものではない。

`deleted_at` は API のレスポンスに含めない（削除済みレコードはクライアントに返さない）。同期用のエンドポイントのみ、差分取得のために `deleted_at` を持つレコードを返す。
