# ADR-0016: マイグレーションはデプロイの前段で自動適用する

- Status: Accepted
- Date: 2026-09-13
- Supersedes: [docs/05-インフラ設計.md](../05-インフラ設計.md) §7 の「適用はデプロイとは分離した手動実行とする」

## Context

当初はマイグレーションを `migrate-db` ワークフローの手動実行に分離していた。理由は「自動適用にすると、失敗時に**アプリが起動しない**と**スキーマ不整合**が同時に起きて切り分けられなくなる」こと。

実際に運用してみると、分離のコストの方が大きかった。

**順序を人が覚えている必要がある。** スキーマはコードより先に進めるのが鉄則で、これはコードが traffic 切り替えで数秒で戻せるのに対し、スキーマは戻せないため。`deploy-api` は main への push で自動起動するので、**マージする前にマイグレーションを流す**ことになる。手動運用では、これを一度でも逆にした時点で「新しいコードが古いスキーマを叩く」時間が生まれる。

30本の PR をまとめて反映する場面（[#144](https://github.com/Kenyan822/physique-analytics/issues/144)）で、この順序が実際に躓きどころになった。手順書に書けば守れる、という前提が成り立っていない。

## Decision

**`deploy-api` の前段ゲートとして自動適用する。**

- `deploy-api.yml` に `migrate` ジョブを足し、`deploy` を `needs: migrate` にする
- **自動で流すのは `up` だけ**
- `migrate-db.yml` は残し、`version` / `down` / dirty からの復旧に使う

### 「切り分けられない」への対処

**`migrate` を別ジョブにする。** 元の懸念は「1つのステップで両方やると原因が分からない」というものだったが、ジョブを分ければログ上で一意に分かる。

| 落ちた場所 | 本番の状態 |
|---|---|
| `migrate` | `deploy` は走らない。**コードもスキーマも無傷** |
| `deploy` | スキーマだけ新しい。追加のみなので**旧コードが動き続ける** |

どちらも「コードだけ戻せば復旧する」を保っている。

### `down` を自動化しない理由

戻せない変更を無人で走らせないため。`down` はデータを落とす可能性があり、失敗の影響がコードのロールバックで回復しない。人が判断して流す。

## Consequences

### 良くなること

- 順序が構造上守られる。人が覚える必要がなくなる
- マージすれば反映が完了する。手順が1つ減る
- 未適用のマイグレーションを抱えたままデプロイされることがなくなる

### 悪くなること・引き受けるリスク

**マイグレーションは追加のみ（expand/contract）にする。** これが最大の制約。

`migrate` → `deploy` の順になるので、**新しいスキーマを旧コードが読む瞬間が必ずできる**。列の削除・リネーム・`not null` 化を1回のデプロイでやると、その瞬間に旧コードが落ちる。分けること。

1. 列を**追加**する（旧コードは無視できる）→ デプロイ
2. コードを新しい列に**切り替える** → デプロイ
3. 古い列を**消す** → デプロイ

現時点の `000001`〜`000011` はすべて追加のみで、この制約を満たしている。

**デプロイのたびに Session pooler へ接続する。** 変更が無ければ `migrate up` は何もしないが、接続自体は毎回発生する。Supabase の接続数は `DATABASE_MAX_CONNS` とは別枠で、デプロイ中の一瞬だけなので問題にならないと判断した。

**`api/**` の変更すべてでマイグレーションが走る。** `deploy-api` の `paths` フィルタは `api/**` なので、マイグレーションと無関係な変更でも `migrate up`（= 何もしない）が走る。無駄だが害はない。

### やらなかったこと

**マイグレーションの有無で `migrate` ジョブをスキップしない。** `api/migrations/**` の差分を見て分岐することもできるが、「差分は無いが前回のデプロイで流し損ねている」場合に取りこぼす。毎回流して no-op にする方が状態が収束する。
