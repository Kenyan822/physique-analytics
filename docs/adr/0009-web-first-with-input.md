# ADR-0009: Web を先行開発し、Web にも入力機能を持たせる

- Status: Accepted
- Date: 2026-09-12
- Supersedes: [ADR-0004](0004-ios-input-web-analysis.md)

## Context

[ADR-0004](0004-ios-input-web-analysis.md) では「iOS = 入力、Web = 分析」と役割を分け、開発順序も iOS（Phase 1）→ Web（Phase 3）としていた。Web に入力を作り込むと両方が中途半端になる、という判断だった。

しかしこの前提には2つの問題があった。

**1. 開発速度を考慮していなかった。** 1人で全てを実装する以上、着手順序は成果物が出るまでの時間を直接左右する。

| | iOS | Web |
|---|---|---|
| 変更の反映 | ビルド 1〜2分 + 実機転送 | リロード数秒 |
| 実機確認 | 必要（HealthKit は実機のみ） | ブラウザで完結 |
| 配信 | TestFlight 審査 | デプロイのみ |
| 学習対象 | Swift + SwiftUI + SwiftData | TypeScript（既知の可能性が高い） |

**2. Web の入力が iOS 完成後も価値を持つことを見落としていた。** PC からの過去データ一括入力・修正、レシピ登録のような長文入力、iPhone が手元にない状況——いずれも Web の方が適している。

## Decision

**開発順序を Web 先行に変更し、Web にも入力機能を持たせる。**

役割分担は「入力 / 分析」ではなく、**「汎用 / ジム特化」**で分ける。

| | Web | iOS |
|---|---|---|
| 位置づけ | **汎用クライアント** | **ジムでの高速入力に特化** |
| トレーニング記録 | ◎ 可能 | ◎ **1セット3秒以内に最適化** |
| 日次記録（体重・PFC） | ◎ 可能 | ◎ 可能 |
| 食事記録 | ◎ 可能（レシピ登録に有利） | ◎ 可能 |
| 週次レポート・グラフ | ◎ **主** | 閲覧のみ |
| 計画管理・月次目標の引き直し | ◎ **主** | × |
| **HealthKit 連携** | **× 不可** | ◎ **iOS のみ** |
| オフライン動作 | △ PWA で限定的 | ◎ **完全** |
| 触覚フィードバック | × | ◎ |

**iOS の存在理由は「ジムでの入力速度」と「HealthKit 連携」に集約される。** これは ADR-0004 の趣旨を引き継いでいる。Web が入力できるようになっても、この2点は Web では代替できない。

### 変更後のフェーズ構成

| Phase | 内容 |
|---|---|
| **1** | **API (Go) + DB + Web**：トレーニング記録・日次記録・週次レポート |
| 2 | iOS：ジムでの高速入力 + HealthKit 連携 |
| 3 | 食事記録・周囲長・写真・計画管理 |
| 4 | Watch 入力・MCP サーバー化・相関分析 |

## Alternatives considered

**A. ADR-0004 のまま（iOS 先行・Web は分析のみ）**
却下。Phase 1 の完了が遅れ、記録開始が遅れる。またスキーマ・API・認証・デプロイといった基盤の検証を、最も反復の遅い iOS で行うことになる。

**B. Web のみで完結させる（PWA）**
却下。HealthKit 連携（体重・体脂肪率・歩数・睡眠・HRV の自動取得）が実現できない。これは既存アプリに対する最大の差別化要素であり（[ADR-0003](0003-build-own-analytics.md)）、放棄できない。

**C. Web を先行するが、入力機能は付けない**
却下。入力できない Web を先に作っても、記録が始まらないため Phase 1 の価値が薄い。

## Consequences

**良い影響**

- **Phase 1 の完了が早まり、記録を早く始められる。** 3年計画において記録開始の遅れは取り返せない
- **基盤（スキーマ・API・認証・デプロイ）を最も反復の速い環境で検証できる。** iOS はその検証済み API に乗るだけになり、Phase 2 のリスクが下がる
- Web の入力機能は iOS 完成後も残り、PC からの一括入力・修正手段として機能する
- OpenAPI によるスキーマ駆動（[ADR-0007](0007-openapi-schema-driven.md)）と組み合わせることで、Phase 1 で確定した API 定義から Swift クライアントを生成でき、Phase 2 の実装量が減る

**悪い影響 / 受け入れるコスト**

- **入力UIを2つ実装・保守することになる。** Web と iOS で同じ機能を別々に作る。ただし API は共通なので、重複するのはUI層のみ
- **Phase 1 のスコープが増える。** API + DB + Web で、当初の「iOS 記録のみ」より広い。§8 で内部を 1a / 1b に分割して対処する
- HealthKit 連携が Phase 2 まで入らないため、**Phase 1 の期間は体重・歩数・睡眠を手入力する**必要がある
