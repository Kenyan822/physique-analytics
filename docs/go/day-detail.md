# 1日ぶんの要約を返す（`GET /v1/days/{date}`）

## 判定を二重実装しない。1日だけの範囲で既存の関数を呼ぶ

**状況**: 日をタップしたときの要約に「達成・未達」と「どれだけ足りないか」を出す。
達成の定義は `/v1/streaks`（`BuildStreak`）にすでにある。

**判断**: `BuildDayMeal` は `BuildStreak(d, d, ...)` を**1日の範囲で呼んで**達成を得る。
自前で「±10% 以内か」を書かない。足すのは、判定に使った目標と、目標との差だけ。

```go
met := BuildStreak(d, d, targets, map[string]PFC{date: consumed}, nil)[0].MealGoalMet
```

**理由**: 同じ定義が2か所にあると、片方だけ直って**カレンダーの印と詳細が食い違う**。
食い違いを防ぐ一番確実な方法はコードを共有すること。そのうえで「境界（ちょうど ±10%）
・目標なし・目標 0 で両者が一致する」テストを置いた。

## 「未達」と「判定できない」は `*bool` で分ける

`GoalMet *bool`。目標が引けない日は `nil`（JSON では `null`）。`false` にすると
「未達」に見えてしまう。同じ理由で `Target` と `Shortfall` も `nil` にする。
`bool` のゼロ値は `false` なので、**3値を表したいときはポインタ**にする
（Python の `Optional[bool]` と同じ発想だが、Go は型で明示しないと自動では区別されない）。

## 集計は SQL に、1行になるものは必ず行が返る

食事の合計は `sum` を `coalesce(..., 0::numeric)` に包むと、**行が無い日でも必ず1行返る**。
`QueryRow` の `ErrNoRows` を分岐せずに、記録が無い日が 0 になる。
一方、体組成のように「行が無い」ことに意味がある（`null` を返したい）ものは
`errors.Is(err, pgx.ErrNoRows)` で `nil` にする。

## 同じ種目が複数セッションにまたがる日は Go でまとめる

SQL は `group by ws.id, s.exercise_id` で素直に引き、**同じ日に別セッションがあれば
`map[uuid.UUID]int`（種目 ID → 結果の添字）でまとめる**。`group by` からセッションを
外すこともできるが、テンプレート名や並び順をセッション単位で決めたいので、集計は2段にした。
