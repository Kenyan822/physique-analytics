# ADR-0001: monorepo 構成を採用する

- Status: Accepted
- Date: 2026-09-12

## Context

このプロジェクトは4つの成果物を含む。

- iOS アプリ（Swift / SwiftUI）— 記録
- Web アプリ（Next.js）— 分析
- 分析ロジック — 週次レポートの生成
- 設計ドキュメント — 要件定義・データモデル・分析仕様

これらをどう配置するかを決める必要があった。開発者は1人。

## Decision

**単一リポジトリ（monorepo）に全てを配置する。**

```
physique-analytics/
├── docs/       設計ドキュメント
├── api/        Go（API・MCP・分析ロジック）
├── ios/        iOS アプリ
├── web/        Web アプリ
└── data/sample/ デモ用データ
```

## Alternatives considered

**A. 3リポジトリに分割**（plan / web / ios）
却下。スキーマ変更が横断するため。「daily_logs に列を追加する」という変更は DB・API・iOS・Web の全てに及び、3リポジトリなら3つのPRに分かれてレビュー単位が壊れる。

**B. 2リポジトリに分割**（計画+分析 / アプリ）
却下。要件定義書とその実装が離れる。`docs/01-要件定義.md` の機能ID（T-01 等）が issue とブランチ名に使われる設計なので、同じリポジトリにある方が追跡しやすい。

## Consequences

**良い影響**

- スキーマ・API仕様の変更が1PRで完結し、変更の全体像がレビューできる
- 要件定義書 → issue → ブランチ → PR のトレーサビリティが1箇所で完結する
- CI 設定が1箇所で済む

**悪い影響 / 受け入れるコスト**

- Xcode（macOS）と Node.js のツールチェーンが同居し、リポジトリのセットアップが重くなる
- Vercel デプロイ時に Root Directory を `web/` に指定する必要がある
- iOS ビルド成果物を確実に `.gitignore` する必要がある（リポジトリ肥大化の防止）
- 将来チームが分かれた場合、分割コストが発生する。ただし1人開発の現時点では発生しない問題であり、**必要になってから分割する**方が安い
