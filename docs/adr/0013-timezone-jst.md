# ADR-0013: 日付は JST 固定で扱う

- Status: Accepted
- Date: 2026-09-12

## Context

このアプリの記録はすべて「日付」に紐づく。体重は1日1回、トレーニングは日単位、週次レポートは7日の集計である。

しかし「今日」の定義を決めていなかった。以下が曖昧なまま実装に入ると、各所でバラバラな解釈が入る。

- **起床直後の体重は日付境界に近い時刻に測る。** 深夜勤務明けの5時と、通常の7時で日付が変わるか
- **海外滞在時にどうなるか。** 現地時間の朝に測った記録は、どの日付になるか
- **週次集計の「週」はいつ始まるか**

これらは後から変更すると、**過去データの日付がずれて分析が破綻する**。最初に決める必要がある。

## Decision

**日付はすべて JST（Asia/Tokyo）で決定する。端末のタイムゾーンに依存しない。**

| 対象 | 型・扱い |
|---|---|
| 「日付」（`daily_logs.date` など） | `date` 型。**JST における日付** |
| 記録時刻（`created_at` / `recorded_at`） | `timestamptz`。UTC で保存 |
| 週の区切り | **月曜始まり**（ISO 8601） |
| クライアントの責務 | **JST で日付を計算して送る**。API は受け取った日付をそのまま使う |

海外滞在中も **JST の日付**で記録する。現地時間では扱わない。

## Alternatives considered

**A. 端末のタイムゾーンで日付を決める**
却下。海外滞在中に記録した日付が現地時間基準になり、**帰国後のデータと時系列が繋がらなくなる**。1週間の旅行で日付が1日ずれると、体重トレンドの線形回帰に歪みが入る。

**B. UTC で日付を決める**
却下。JST は UTC+9 なので、**日本時間の 0:00〜9:00 の記録が前日扱いになる**。起床直後の体重測定（6〜8時）がちょうどこの時間帯に入るため、最も重要な記録が毎日前日にずれる。

**C. 記録時に手動で日付を選ばせる**
却下。入力速度（1セット3秒以内）を損なう。毎日の記録で日付選択を挟むのは摩擦が大きい。

## Consequences

**良い影響**

- **タイムゾーンをまたいでもデータが連続する。** 海外滞在中の記録も同じ時系列に乗る
- 「今日」の定義が1つに定まり、クライアント・API・分析で解釈が揃う
- 週次集計の境界が安定する

**悪い影響 / 受け入れるコスト**

- **海外滞在中は「現地の朝」と「記録上の日付」がずれる。** 例えばフィンランド（UTC+2）の朝7時は JST 14時なので同日になるが、**現地の深夜〜早朝（JST では前日の夕方〜夜）に記録すると前日扱いになる**
- 将来、日本以外に長期滞在する場合は再検討が必要になる。その場合は本 ADR を Superseded とする
- クライアント側で JST への変換を実装する必要がある（端末が別のタイムゾーンに設定されていても JST で計算する）

## Notes

**時刻そのものは `timestamptz` で保存する**ため、後から「何時に記録したか」の分析はできる。例えば「起床時刻と体重の関係」を見たくなった場合、日付とは別に時刻を参照すればよい。

日付を JST 固定にするのは**集計の単位を安定させるため**であり、時刻情報を捨てるわけではない。
